# AZRAIL OS — MVP

Автономная система разработки на Cloudflare (Workers + Agents SDK + D1 + KV + R2 + Workers AI).
MVP-объём по разделу 2 системного промпта: **Orchestrator → Code Agent → Deploy Agent**.
Security/QA/UI/Database/Architect агенты — следующая итерация, не входят в MVP осознанно.

## Инфраструктура (проверено 2026-08-08)

| Ресурс | Имя | ID/статус |
|---|---|---|
| Worker | `azrail-os` | уже задеплоен (замещается этой сборкой) |
| D1 | `azrail-db` | `c76e7d92-648c-45bc-b0df-f26b00d0ff88` — схема применена и сверена: `users`, `projects` (обе — расширены `ALTER TABLE` под нужные колонки), `project_versions`, `task_history`. Есть неиспользуемая `sessions` от более ранней сессии — не трогал |
| KV | `AZRAIL_KV` | `dab3b792264f4d9cbec5d637d4f8d71e` |
| R2 | `azrail-artifacts` | существует |
| Queue | — | **не создана**, см. «Пробелы» |
| Vectorize | — | **не создан**, см. «Пробелы» |

## Архитектура

```
index.ts (fetch handler)
  └─ Orchestrator (Durable Object, единственный явный биндинг)
       ├─ checkSufficiency()   — Шаг 2: не домысливать за пользователя
       ├─ classifyIntent()     — эвристика по input_type + AI-фоллбек на свободный текст
       ├─ subAgent(CodeAgent)   — analyze_spec / review_repo / generate_code / unclear
       └─ subAgent(DeployAgent) — deploy
```

Code Agent и Deploy Agent — `subAgent()`, не отдельные DO-биндинги: общий рантайм с
оркестратором, но изолированное состояние/SQLite каждого. Так короче wrangler.toml
и не нужно по три миграции на агента.

### Слой автономного выполнения

Появился позже основной схемы и работает рядом с ней, а не вместо неё.
`/api/task` — один проход агента. `/api/mission` — цикл: модель выбирает
инструмент, движок исполняет, результат возвращается модели, и так до
завершения или до потолка шагов.

```
core/execution-engine.ts   — сам цикл + адаптеры инструментов
lib/tool-registry.ts       — что AZRAIL умеет и какой ценой (safe/review/approval)
lib/workspace.ts           — файловые операции проекта поверх R2
lib/chat-store.ts          — переписка в D1, с parent_message_id под ветвление
lib/event-store.ts         — события миссии; их же видит карта шагов в интерфейсе
```

Три границы вшиты намеренно и держатся тестами:

- Инструменты риска `approval` цикл исполнить не может — их нет в
  `availableTools()`, и `executeTool` отказывает по флагу. Необратимое
  требует отдельного решения владельца, а не согласия модели с самой собой.
- `maxIterations` — жёсткий потолок, не пожелание.
- Исчерпанный потолок возвращает `needs_input`, а не `done`: недоделанную
  задачу нельзя выдавать за выполненную.

`ExecutionEngine` — обычный класс, не Durable Object, поэтому `subAgent()`
ему недоступен. Инструменты `git_diff` и `run_tests` идут через
`Orchestrator.invokeCapability()` — тот же `runCapability`, что обслуживает
обычные задачи. Второй путь к GitHub API не заводится: это была бы вторая
копия проверок и будущее расхождение между ними.

### Внешние зависимости

Главная страница (`public/index.html`) их НЕ имеет: ни одного `src` или
`import` на внешний адрес. Проверяется тестом — раньше оттуда грузился
three.js ради фона, и без сети страница теряла оформление.

Старая панель (`public/classic.html`) тянет Mermaid с CDN для отрисовки
диаграмм Architect Agent. Оставлено сознательно: это функция, а не
украшение, и она честно вырождается — при недоступном CDN диаграмма
показывается исходным текстом, страница не ломается.

### Песочница и проверка качества

`done` больше не мнение модели. Если в истории миссии есть прогон тестов,
решение принимается ПО НЕМУ — модель не спрашивается вовсе. Спрашивать её
поверх упавших тестов вредно: она объяснит, почему падение неважно, и
объяснение прозвучит убедительно. Числа обсуждению не подлежат.

Движок исполнения сменный (`core/sandbox.ts`):

| Движок | Когда доступен | Что умеет |
|---|---|---|
| `container` | платный план Cloudflare | произвольные команды, секунды |
| `actions` | задан `GITHUB_TOKEN` | только описанные workflow, минуты |
| `none` | ничего из этого | проверка падает на мнение модели |

Доступность инструментов `sandbox_*` вычисляется по среде, а не зашита:
через Actions доступен только `sandbox_test`, потому что произвольные
команды и предпросмотр там невозможны.

Разбор вывода тестов устроен с важной асимметрией: непонятный вывод
НИКОГДА не считается успехом — итог берётся из кода возврата. В разборе
вердикта проверяющего наоборот, непонятное считается прохождением. Причина:
там проверка — надстройка и не должна блокировать сделанную работу, здесь —
основание для решения.

## Аудит перед деплоем — что было найдено

Пофайловый разбор нашёл 7 настоящих ошибок, из них две — ломающие
функциональность молча:

1. **`/api/agents` был открыт.** Роут числился в списке защищённых, но
   обрабатывался ВЫШЕ проверки доступа и отвечал всем. Ровно тот класс
   ошибки, от которого комментарий рядом обещал уберечь.
2. **Внешние ключи роняли всю персистентность.** `project_versions`,
   `task_history` и `project_memory` ссылаются на `projects(id)`, а строка
   проекта не создавалась нигде. В D1 внешние ключи включены — каждая
   вставка падала бы. Молча: всё обёрнуто в `try/catch` с комментарием
   «не роняем задачу из-за аналитики». Симптом выглядел бы как «Evolution
   Agent ничего не находит», и причину искали бы не там. Цепочка оказалась
   двухуровневой (`users ← projects ← остальные`) — первая версия фикса
   чинила только нижний уровень и падала сама.
3. **В историю всегда писался `agent: "orchestrator"`**, кем бы задачу ни
   выполнили. Evolution Agent группирует повторяющиеся сбои именно по этому
   полю — его главная функция была сломана.
4. **XSS через вывод модели.** Значения из памяти проекта — текст,
   сгенерированный моделью — вставлялись в дашборд через `innerHTML`.
   Плюс имя загруженного файла и строки истории. Все три переведены на
   построение DOM с `textContent`.
5. **`projectId` из URL не декодировался** — клиент шлёт
   `encodeURIComponent`, сервер читал сырой сегмент. Для id с пробелом
   чтение никогда не совпало бы с записью.
6. **Гонка в нумерации версий** — `SELECT MAX` и `INSERT` не атомарны.
   Теперь номер вычисляется внутри вставки.
7. **Не было лимита размера тела** у `/api/task`.

Проверено не только компилятором: цепочка записи прогнана на живой D1 —
создание проекта, инкремент версий, обновление агента в истории, апсерт
памяти. Тестовые строки удалены.

На каждую ошибку написан регрессионный тест (`tests/regressions.test.ts`) —
они существуют потому, что баг был, а не «на всякий случай».

## Второй проход аудита

Повторный разбор после добавления самопроверки и редизайна нашёл ещё пять
вещей. Две из них — про саму самопроверку, то есть про код, написанный
специально чтобы ловить ошибки:

1. **Проверка, которая не могла упасть.** `ping()` читал `this.state`, чтобы
   доказать доступность хранилища. Чтение исходников SDK показало, что геттер
   состояния ходит в SQLite только при первом обращении, а дальше отдаёт кеш
   (`if (this._state !== DEFAULT_STATE) return this._state`). На тёплом
   экземпляре проверка всегда проходила бы, ничего не проверяя. Заменено на
   прямой `SELECT 1` к хранилищу Durable Object. Проверка, которая не может
   упасть, хуже отсутствия проверки: она даёт ложную уверенность.
2. **Агент со сломанным хранилищем считался здоровым.** `ok` выставлялся в
   `true` по факту ответа на ping, независимо от того, что этот ответ
   сообщал. Теперь состояние хранилища входит в итог.
3. **Два источника правды об агенте.** Реестр называл его `architect` версии
   `1.0`, сам агент в ping — `architect-agent` версии `1.0.0`. Личность
   убрана из агента целиком: он сообщает только то, что может знать про себя.
4. **`recordHistory` зависела от порядка вызовов** — полагалась на то, что
   проект уже создан вызывающим. Сегодня это было так, но именно эта
   хрупкость (запись в таблицу с внешним ключом без строки-родителя) уже
   стоила проекту всей персистентности. Функция сделана самодостаточной.
5. **Мелочи дашборда:** мёртвый CSS-селектор, класс `medium` применялся без
   правила (выглядело как забытое), значение из данных шло прямо в
   `className`.

## Четвёртый проход аудита

Разбор файлов, которым в прошлые проходы уделялось меньше всего внимания
(QA Agent, Git Agent, source-reader, memory-agent). Главная находка —
не отдельная ошибка, а **класс уязвимостей**.

### Подстановка в URL без проверки

Тело запроса приходит по HTTP как JSON и приводится к типу простым
`await request.json()`. **Типы TypeScript при этом стираются**: поле,
объявленное как `runId: number`, в рантайме может быть строкой. А дальше
оно подставлялось прямо в путь запроса к GitHub.

Проверено на живом `URL`: конструктор нормализует `..`, поэтому

```
/repos/owner/name/actions/runs/1/../../../../user/repos/jobs
```

превращается в `/user/repos/jobs` — запрос уходит на **другой эндпоинт**,
и уходит с токеном GitHub из секретов воркера.

Затронуто было шесть мест: `runId` в QA Agent, путь файла и имя ветки в
Git Agent, `owner/repo` в source-reader (разбирался простым `split("/")`
вообще без проверок), плюс репозиторий в Deploy Agent.

Точечные заплатки для такого не годятся — их забывают ровно там, где
добавляют новый эндпоинт. Поэтому появился общий барьер
`src/lib/safe-path.ts`, через который проходит любое значение, попадающее
в путь. Тест следит, чтобы ни один агент не подставлял значения в URL
напрямую — и он же нашёл место, которое я пропустил при первом проходе
правок.

### Остальные находки

- **Служебная разметка памяти утекала пользователю.** `stripMemoryBlock`
  работал без флага `g` и убирал только ПЕРВЫЙ блок `---MEMORY---`; если
  модель выдавала два, второй попадал в текст ответа. По той же причине
  терялись факты из всех блоков кроме первого.
- **Нельзя было удалить ошибочный факт из памяти.** Пишут её пять агентов,
  а способа убрать неверную запись не было вовсе — при том что память
  подмешивается в промпт при КАЖДОЙ будущей задаче по проекту. Одна
  галлюцинация модели тихо отравляла бы всю дальнейшую работу, и чинить
  пришлось бы руками в базе. Добавлен маршрут `DELETE`, под авторизацией.
- **Мусорная категория факта исчезала бесследно** — теперь пишется в лог.
- **Мёртвый код** (`timed`, `findById`) удалён.

## Третий проход аудита

Разбор после сборки маршрутизатора нашёл семь ошибок, две из которых
отменяли только что построенную защиту:

1. **Слой ретраев отменял защиту от квоты.** `withRetry` считает 429
   обычной временной ошибкой и повторял ТУ ЖЕ модель с задержкой, прежде
   чем маршрутизатор успевал распознать исчерпанный лимит и уйти на
   другую. Проверено симуляцией: было два обращения к закрытой двери,
   стало одно. У `withRetry` появился параметр `retryable`, которым
   вызывающий переопределяет решение о повторе, когда знает про ошибку
   больше, чем видно в её тексте.
2. **`isQuotaError` отстранял рабочие модели.** Голая подстрока
   `insufficient` ловила `insufficient permissions` — ошибку ДОСТУПА;
   `capacity` ловила `capacity planning`. Каждый такой случай парковал
   исправную модель на пять минут: защита от недоступности сама создавала
   недоступность. Заменено точными шаблонами, обе стороны закрыты тестами.
3. **Простой проверялся у всего реестра на каждом вызове** — по одному
   чтению KV на модель перед КАЖДЫМ запросом. Теперь сначала бесплатный
   отбор в памяти, а проверка простоя только у прошедших: обычно
   два-четыре чтения вместо всего каталога, и не растёт с его размером.
4. **Показ маршрута расходился с поведением.** `route` не знал про шлюз, и
   самопроверка — первое, что жмут после деплоя — сообщала бы выбранной
   стороннюю модель, которую в момент вызова пропустили бы. Теперь
   доступность шлюза передаётся явно, а `route` остаётся чистой функцией.
5. **Пустой ответ модели принимался.** Агент молча продолжал работу с
   пустотой, и это выглядело как «модель ответила плохо», хотя она не
   ответила вовсе. Добавлена базовая проверка, которую агент не может
   забыть.
6. **Отклонённый ответ и отсутствие ответа сообщались одинаково** —
   отладка уходила не туда. Плюс сбой в самой функции проверки выглядел
   как отказ модели: баг в валидаторе месяцами списывался бы на провайдера.
7. **Флаг-пустышка у `classify`** — политика там и так дешёвая, и флаг
   обещал разное поведение на мелких и обычных задачах, хотя порядок один.

Заодно всплыл практический риск, вынесенный в самопроверку: **без
`AI_GATEWAY_ID` четыре типа задач остаются на одной модели без запасной.**
Дашборд теперь помечает такие маршруты красным — исчерпается лимит, и
задачи этого типа просто перестанут выполняться.

## Выбор модели (AI Router)

Слаги моделей живут **в одном месте** — `src/lib/model-registry.ts`.
Ни агенты, ни `wrangler.toml` их больше не содержат.

**Маршрутизация идёт по фактам, а не по оценкам.** Рейтингов вида
«97 против 95» здесь нет намеренно: таких чисел не существует, их нельзя
измерить, а решение, опирающееся на выдуманную цифру, невозможно отладить —
когда маршрутизатор выберет не то, причину не восстановить.

Вместо этого:

1. **Жёсткий фильтр по возможностям** — задаче нужен tool calling, значит
   модели без него отсеиваются. Это факт из каталога, а не мнение.
2. **Порядок задаётся политикой**, которую ты пишешь сам и читаешь целиком
   за минуту (`ROUTING_POLICY`). Для кода — `frontier → balanced → fast`,
   качество приоритетнее. Для классификации намерения — наоборот: она
   вызывается на каждом свободнотекстовом запросе, и одно слово на выходе
   от дорогой модели точнее не станет.
3. **Каждое решение объяснено.** Отбракованные модели попадают в лог с
   причиной. Если выбор окажется неверным, видно, на каком шаге он свернул.

**У каждой записи реестра указан источник данных.** Поле, которое проверить
не удалось, отсутствует — а не заполняется правдоподобным значением.
Отсутствующее окно контекста означает «не проверено», и маршрутизатор по
нему не фильтрует, но пишет это в объяснение. Причина жёсткости: в этом же
проекте слаг, вписанный по памяти, оказался снятым с поддержки, и
классификатор работал бы на мёртвой модели.

**Fallback между моделями** отличается от ретраев: `withRetry` повторяет ТУ
ЖЕ модель, что лечит сетевую икоту; маршрутизатор переходит на ДРУГУЮ, что
лечит недоступность, исчерпанный лимит и снятие модели с поддержки.

**Сторонние модели** (`anthropic/*`, `openai/*`) требуют `AI_GATEWAY_ID` —
без него доступны только собственные модели Cloudflare. Своих ключей
провайдеров не нужно: оплата идёт с баланса аккаунта через Unified Billing.

### Исчерпание лимита

Отказ по квоте отличается от прочих сбоев: повторять ту же модель
бессмысленно не только сейчас, но и ближайшие минуты. Такая модель
отмечается в KV с TTL и пропускается при следующих запросах, пока не
истечёт срок — запись исчезает сама, «застрять» в отстранении модель не
может даже при сбое. Если провайдер прислал `Retry-After`, берётся его
значение (с потолком в час: сутки без сильной модели из-за странного
заголовка хуже одной лишней попытки).

### Выбор по сложности — и почему он устроен так

Соблазн — спросить модель, насколько задача сложна. Но тогда платишь
лишний вызов ради выбора вызова, и экономия сводится в ноль.

Поэтому сложность оценивается по **бесплатным сигналам**: объём входа,
число файлов, наличие готового плана архитектуры. Сигналы намеренно грубые
и объявлены таковыми в коде — объём не равен трудности, «перепиши слой
авторизации» короче описания опечатки на две страницы.

Из этого следует главное ограничение: оценка используется **только чтобы
разрешить дешёвый старт на явно мелких задачах** и никогда — чтобы
запретить сильную модель. Ошибка в сторону «взяли дорогую зря» стоит
одного вызова; обратная портит результат.

**И вместо догадки — проверка.** Агент передаёт маршрутизатору структурную
проверку ответа: у UI Agent это наличие блоков `---FILE:---`, у
классификатора — присутствие известной метки намерения. Если дешёвая
модель вернула непригодное, запрос поднимается на сильную. Для мелких
задач цепочка идёт снизу вверх, поэтому подъём получается сам собой —
отдельного механизма эскалации не нужно.

Проверка обязана быть структурной и бесплатной. Оценивать *качество* могла
бы только другая модель — а это уже плата за то, что мы пытались
сэкономить. Удешевление разрешено лишь там, где провал детектируем: у
`review_repo` такой проверки нет, поэтому дешёвый старт для него запрещён —
иначе это была бы тихая потеря качества.

**Чего здесь сознательно НЕТ:**

- *Своей статистики по стоимости, задержкам и ошибкам.* Это уже делает AI
  Gateway, причём точнее. Дублировать платформу — писать худшую копию.
- *Режима совета нескольких моделей.* Тройная цена плюс отдельный вызов на
  «судью», при недоказанной пользе. Вернуться к этому имеет смысл, когда
  накопится статистика Gateway и станет видно, где расхождение моделей
  реально что-то даёт.

## Условия работы subAgent

Найдено при подготовке к деплою, чтением исходников агентского SDK, и с тех
пор доведено до конца реальным деплоем — ниже settled-версия, не гипотеза.

1. **Флаг `experimental` — НЕ нужен и НЕ должен стоять.** `subAgent()` в
   исходнике первым делом проверяет `ctx.facets`/`ctx.exports` и текстом
   собственной ошибки требует этот флаг. Из-за этого он был добавлен в
   `compatibility_flags` заранее. Реальный CI (2026-08-23) отклонил такой
   деплой на уровне Cloudflare: `"The compatibility flag experimental is
   experimental and cannot yet be used in Workers deployed to Cloudflare"`
   (код 10021) — флаг нельзя использовать вообще, не только "не нужен".
   Флаг убрали, передеплоили, и самотест прошёл 11 из 11: все девять
   агентов поднимаются через `subAgent()` без него. Требование в тексте
   ошибки SDK для уже задеплоенных Workers оказалось неверным — вероятно,
   потому что API `ctx.exports` включён по умолчанию для дат совместимости
   от 2025-11-17, а у проекта `compatibility_date = "2026-08-08"`.
   Если флаг когда-нибудь снова окажется в `wrangler.toml` (например, из
   старого ZIP-бэкапа — так уже случалось) — это регрессия, убрать не
   раздумывая, деплой с ним падает гарантированно.
2. **Экспорт классов из точки входа.** Агент ищется как
   `ctx.exports[cls.name]`; не найдя, SDK бросает
   `Sub-agent class ... not found in worker exports`. Все восемь классов
   теперь экспортируются из `src/index.ts`. Имена экспортов должны точно
   совпадать с именами классов: сопоставление идёт по `cls.name`, поэтому
   переименование через `as` сломало бы подъём агента в рантайме, не сломав
   сборку.

Отдельных записей в `[[migrations]]` дочерним агентам не нужно: `subAgent`
поднимает их как facets внутри `Orchestrator`, а не как самостоятельные
Durable Objects. Проверено, что все девять классов присутствуют в экспортах
собранного бандла.

## Самопроверка

```
POST /api/selftest      (нужен токен, модели не вызываются)
```

Или кнопка «Проверить систему» в дашборде. **Это первое, что нужно нажать
после деплоя.**

Проверка поднимает каждого из восьми агентов через `subAgent()` и вызывает
у них `ping()`, затем прогоняет полную цепочку записи в D1 (создание проекта
через внешние ключи → вставка → чтение обратно → удаление), а также запись
и чтение в KV и R2. За собой убирает.

**Зачем она нужна именно до первого деплоя.** `subAgent()` использован в коде
девять раз и до деплоя не выполнялся ни разу. Если он ведёт себя не так, как
предполагалось — например, дочерним классам нужны собственные записи в
`migrations` — то все девять агентов упали бы одинаково, с текстом «задача не
выполнена». Причину пришлось бы искать перебором. Здесь же сразу видно, какой
именно агент не поднимается и с какой ошибкой.

`ping()` объявлен в обязательном контракте `RunnableAgent`, а не отдельным
хелпером: агент, попавший в реестр без него, не соберётся. Модели проверка не
трогает, поэтому бесплатна — жать можно сколько угодно, что и требуется в
первые минуты после деплоя.

## Визуальный язык

**Принцип: спящее — серое, работающее — светится.** Это не приём оформления,
а отражение того, как система устроена. Durable Objects поднимаются по
запросу и засыпают — поэтому агенты в реестре помечены «в реестре», а не
«онлайн». Интерфейс говорит то же самое: почти всё на экране приглушено,
фиолетовый появляется там, где что-то живо.

Фиолетовый работает как источник света в тёмной комнате, а не как заливка.
Площадь применения намеренно мала — это отличает премиальную панель от
типовой «AI-панели с градиентом». Пара `#6366F1 → #A855F7` в градиенте
сегодня читается как штамп; здесь одна лампа `#9A6BFF` и её приглушённая
версия для границ.

Основа — не чистый чёрный: `#09070D` с фиолетовым подтоном. Чистый `#000`
на экране читается плоско, подтон даёт глубину, не заявляя о себе.

**Типографика.** Syne (700/800) — только на логотипе и заголовках секций,
не более двух десятков появлений на странице; это шрифт афиш европейской
электронной сцены, и он здесь как голос бренда. Всё остальное — JetBrains
Mono. Моноширинный для всего содержимого оправдан тем, что на странице
почти нет прозы: подписи, значения, код.

**Структура.** Секции — плоские полосы, разделённые волосяными линиями, без
плавающих карточек и теней. Карточка с тенью — язык типовой панели; здесь
всё лежит на одной плоскости.

**Сигнатура — линия пульса.** Полоса в 1px под шапкой. В покое ровная и
тусклая; пока идёт запрос, по ней проходит световая волна. Состоянием
управляет счётчик активных запросов в единой точке `api()` — флаг гасил бы
линию по завершении первого из параллельных запросов. Название бренда
(mnmll**pulse**) и реальное состояние системы сошлись в одном элементе. Это
единственное место, где интерфейс повышает голос.

**Доступность проверяется расчётом, а не на глаз.** Первая версия палитры
давала приглушённому тексту 3.76:1 при норме WCAG AA 4.5:1 — заметил это
только расчёт контраста. Значение поднято до 5.13:1 и проверено на всех трёх
поверхностях (промежуточный вариант давал на панелях 4.40:1 и нормы не
проходил). Тесты считают контраст формулой при каждом прогоне.

## Тесты

```bash
npm test          # один прогон
npm run test:watch
```

447 теста: чистая логика + регрессии на найденные ошибки. Логика —: парсер файлов UI Agent (включая path traversal),
скан секретов (в т.ч. отсутствие ложных срабатываний на хешах и base64),
разбор блока памяти, парсинг зависимостей, отставание версий, санитизация
имён файлов, классификация ошибок для ретраев, таймауты, полнота реестра
(каждый intent находит агента).

Рантайм Cloudflare не мокается: модули `cloudflare:*` подменяются заглушкой
(`tests/stubs/`), чтобы граф импортов вообще загрузился в Node. Всё, что
реально зависит от рантайма — D1, KV, R2, вызовы моделей — здесь **не
проверяется**, и это осознанное ограничение: такие вещи подтверждает только
живой деплой.

Первый же прогон нашёл настоящий недочёт: `sanitizeFilename("../../evil.zip")`
давал `.._.._evil.zip` — слэши убирались, точки оставались. В R2 это
безвредно (ключи плоские), но имя стало бы опасным в файловом контексте.
Исправлена функция, не тест.

## Защита и устойчивость

**Авторизация — fail-closed.** `/api/task`, `/api/upload`, `/api/agents` и
`/api/projects/*` требуют `Authorization: Bearer <AZRAIL_TOKEN>`. Если секрет
не задан — эндпоинты отвечают 503 с инструкцией, а не работают открыто.
Причина: у Worker'а публичный URL, и без проверки любой, кто узнает адрес,
запускает Nemotron 120B за твой счёт. Забытая настройка не должна означать
открытый кошелёк.

Проверка стоит **одним местом** перед группой роутов, а не в каждом — так
новый эндпоинт физически не может оказаться незащищённым по забывчивости.
Сравнение токенов не зависит от позиции первого различия (иначе токен
теоретически подбирается по времени ответа).

`/health` и дашборд остались публичными: они ничего не тратят, а мониторингу
токен взять негде.

**Лимит расхода.** Счётчик задач в час на вызывающего, в KV, ответ 429 с
временем сброса. Окно фиксированное по часам, а не скользящее — скользящее
требует хранить таймстемпы каждого запроса, что дороже самой защиты. На
границе часа лимит можно превысить почти вдвое; это осознанный компромисс,
и он проговорён в коде.

**Таймауты.** Каждая попытка ограничена по времени (по умолчанию 60 с).
Ретраи лечат *упавшее*, но не отменяют *повисшее*: без таймаута один зависший
вызов съедал бы лимит запроса целиком. Важно понимать ограничение: подлежащий
промис по-настоящему не прерывается — мы перестаём его ждать.

**Ретраи.** Все пять вызовов моделей обёрнуты в `withRetry` с экспоненциальной
задержкой и джиттером. Джиттер не для красоты: без него параллельные задачи
повторяются синхронно и бьют по уже перегруженному сервису одной волной.
Постоянные ошибки (400/401/404, «не найден») **не** ретраятся — ответ не
изменится, а время и деньги потратятся.

**Логи.** Одна строка = один JSON-объект (`ts`, `level`, `event` + контекст).
Смотреть: `npx wrangler tail`. В Worker'е нет отладчика, и это единственный
способ понять, что произошло в проде; без структуры там была бы простыня.

## Agent Registry + Capability System

`src/lib/agent-registry.ts` — единый реестр. Orchestrator больше не знает
агентов поимённо: он спрашивает «кто умеет `architecture`?» и получает класс.
Раньше здесь была цепочка `if/else` на восемь веток, и добавление агента
требовало правки маршрутизации; теперь — одна запись в реестре.

Что это дало по факту:
- **Единый контракт `run()`.** У Architect метод назывался `plan()` —
  переименован. Без единого имени реестр невозможен в принципе.
- **Типобезопасность реестра.** `AgentClass` — пересечение двух условий:
  наследует `Agent` (иначе `subAgent()` не примет) И реализует `run()`.
  Класс без `run()` в реестр не положить — ошибка на компиляции, не в рантайме.
- В маршрутизации осталось ровно два `if` — те, где задача действительно
  образует **цепочку** из двух агентов (architecture→code, ui→git), а не
  сводится к одному вызову.

`GET /api/agents` отдаёт реестр; дашборд его показывает.

**Статуса `online` в реестре намеренно нет.** Агенты — это Durable Object'ы,
которые поднимаются по требованию и heartbeat не шлют. Поле называется
`registered` и значит ровно это. Зелёная лампочка «online» была бы
нарисованной.

## Health Monitor

`GET /health` раньше проверял только наличие биндинга (`!!env.AZRAIL_D1`) —
и показывал «всё зелено» даже когда D1 недоступна. Теперь делает **реальные
round-trip запросы** к D1 (`SELECT 1`), KV (`get`) и R2 (`head`), с замером
времени ответа и текстом ошибки. Общий статус — `healthy` / `degraded`,
и при `degraded` эндпоинт отвечает **503**, а не 200 с грустным полем внутри.

AI / Vectorize / Queue намеренно **не** пробуются запросом: вызов модели ради
health-check стоит денег, а `put` в очередь порождал бы мусорные сообщения.
Для них показывается только наличие биндинга — и в дашборде они помечены
`bound*` с отдельной подписью, чтобы это не читалось как «проверено».

## Evolution Agent

Отличие от Code Agent: тот видит **снимок** кода, этот видит **траекторию** —
что ломалось повторно, какие `known_issue` висят непочиненными, сколько версий
артефактов накопилось. Такие выводы нельзя сделать из одного состояния
репозитория, только из накопленной в D1 истории. Поэтому он и стоит последним
в дорожной карте: в первый день работы системы анализировать нечего, и агент
честно возвращает `needs_input`, если истории нет.

Что делает:
1. Читает `task_history`, `project_memory`, `project_versions` по projectId.
2. Считает **повторяющиеся** сбои (сгруппированные по агенту + сигнатуре
   ошибки). Единичные отфильтровываются — повторившийся сбой информативнее.
3. Детерминированно проверяет свежесть зависимостей по npm registry: отставание
   major/minor/patch, флаг `deprecated`, сколько лет без релизов.
4. Только поверх этих **реальных** агрегатов зовёт модель для синтеза, с явным
   запретом выдавать общие советы по разработке за анализ проекта.

Если модель недоступна — детерминированная часть всё равно отдаётся, а не
теряется вместе с запросом.

**Источник проверен живьём** (в отличие от OSV и GitHub Actions API): формы
ответов `registry.npmjs.org` сверены реальными запросами — `dist-tags.latest`,
флаг `deprecated` на версии, `time[version]` с датой релиза.

## QA Agent

**Ограничение, которое не обходится:** Worker не запускает процессы — ни
`npm test`, ни линтер, ни сборку. Агент, заявляющий «я прогнал тесты», в этой
среде врал бы. Поэтому QA Agent делает две реальные вещи вместо одной ложной:

1. **Драйвит чужой раннер.** `trigger_tests` запускает GitHub Actions workflow
   (`workflow_dispatch`), `latest_run` отдаёт статус последнего прогона,
   `check_run` вытаскивает упавшие джобы **и конкретные упавшие шаги** (без
   них «job failed» бесполезен). Тесты выполняет CI, AZRAIL ими управляет и
   читает результат — это честная граница.
   Нюанс: GitHub на `workflow_dispatch` отвечает 204 без тела и **не отдаёт id**
   запущенного прогона, поэтому за статусом надо идти отдельным `latest_run`.
2. **Структурный анализ покрытия** (`coverage_gaps`, по умолчанию): какие
   модули не упоминаются ни в одном тест-файле. Считается по файловой
   структуре, без выполнения кода. Это **не** метрика покрытия строк, и в
   ответе так и написано — `data.method` проговаривает метод явно, чтобы
   цифру не приняли за coverage %.
   Индексные/типовые файлы (`index.ts`, `types.ts`, `*.d.ts`) из подсчёта
   исключены — считать их «модулями без тестов» бессмысленно.
   Проверено отдельным прогоном: фильтры и сопоставление тест↔модуль дают
   ожидаемый результат, включая случай «тестов нет вообще».

`coverage_gaps` — единственная QA-операция, которой нужны исходники, поэтому
в Шаге 2 Orchestrator проверяет её как обычную задачу, а операции к GitHub
Actions пропускает как самодостаточные.

## Security Agent

Сознательно **не** делает AI-ревью на XSS/SQLi/SSRF — это уже в системном
промпте Code Agent, и второй агент с тем же промптом был бы переклейкой
вывески. Делает то, чего модель надёжно не может:

1. **CVE-скан зависимостей через OSV.dev.** Парсит `package.json` /
   `requirements.txt` / `Cargo.toml`, батч-запросом проверяет по живой базе,
   догружает детали (severity, в какой версии пофикшено). Модель не знает
   уязвимости, вышедшие после обучения, и склонна выдумывать идентификаторы —
   поэтому живой источник, а не промпт.
2. **Скан утёкших секретов.** Regex по провайдерским префиксам (AWS, GitHub,
   Stripe, OpenAI, Anthropic, Slack, приватные ключи) + общий паттерн
   присваивания. С номерами строк, **значения маскируются** — полный секрет не
   уходит ни в ответ, ни в логи. `.env.example`, `.md` и плейсхолдеры
   (`your-key-here`, `changeme`, `${...}`, `process.env...`) пропускаются.

Протестировано отдельным прогоном на ложных срабатываниях: SHA-хеши и base64
не ловятся, файлы-образцы и документация пропускаются, дубли (один секрет,
пойманный и провайдерским, и общим паттерном) схлопываются в более
специфичную находку.

Если OSV недоступен — это отдельно проговаривается в ответе, а не выдаётся за
«уязвимостей нет».

Найденные секреты записываются в память проекта как `known_issue` — чтобы
всплыли в следующих задачах, а не потерялись в одном отчёте.

**Честно про источник:** формы запросов OSV взяты по знанию API, живыми
запросами не проверены — песочница, где писался код, не пускает `api.osv.dev`.
У Worker'а в проде такого ограничения нет. Проверяется одним запуском на любом
`package.json` с зависимостями.

## Общий ридер исходников

`src/lib/source-reader.ts` — чтение ZIP/PDF/DOCX/GitHub/текста, вынесено из
`CodeAgent.gatherContext()`, когда появился второй потребитель. Отдаёт
структуру `{path, content}[]`: Security Agent сканирует пофайлово (нужен путь
и строка), Code Agent склеивает в блоб для промпта через `joinForPrompt()`.

## UI Agent

Отличие от Code Agent — не вывеска, а формат выхода: Code Agent возвращает
**текст разбора**, UI Agent возвращает **файлы** — массив `{path, content}`,
который напрямую уходит в Git Agent без ручного копипаста.

```json
POST /api/task
{ "inputType": "text", "intent": "generate_ui",
  "payload": "Экран истории задач со статусами и фильтром",
  "designBrief": "тёмный, техничный, без градиентов",   // опц.
  "commitToBranch": "feature/ui",                        // опц. — сразу коммитить
  "gitRepo": "owner/name" }
```

Системный промпт заставляет модель работать в два прохода: сначала дизайн-план
(палитра, типографика, лейаут, signature-элемент), потом самопроверка на
шаблонность, и только потом код. Плюс явный список типовых AI-дефолтов, которых
надо избегать без прямого запроса — иначе на любой бриф выходит один и тот же
интерфейс.

Файлы парсятся из блоков `---FILE: path--- ... ---ENDFILE---`. Парсер
протестирован на краевых случаях: несколько файлов, ведущий слэш, пустое
содержимое, маркеры внутри строкового литерала, и **path traversal** (`../`
отсеивается — иначе сгенерированный путь мог бы уехать в коммит куда угодно).
Если модель не вернула ни одного файла — это `failed`, а не «успех с текстом»:
угадывать код из свободного текста агент не будет.

`commitToBranch` — строго опционален. Молча коммитить сгенерированное моделью
в ветку нельзя, поэтому без явного указания файлы только возвращаются в ответе.
Коммит идёт по файлу за раз (Contents API атомарен на файл), статус каждого
виден отдельно — частичный успех не прячется.

## Git Agent

Работа с GitHub через REST API — платформенных ограничений нет, всё делается
из Worker'а напрямую (в отличие от build/test у Deploy Agent).

Операции (`gitOp` в теле запроса): `create_branch`, `commit_file`, `open_pr`,
`diff`, `list_commits`. Операция всегда **структурная** — Git Agent не парсит
намерение из свободного текста и не гадает, что именно коммитить: без `gitOp`
возвращает `needs_input` со списком форм.

```json
POST /api/task
{ "gitRepo": "owner/name",
  "gitOp": { "type": "create_branch", "branch": "feature/x", "from": "main" } }
```

Репозиторий берётся из `gitRepo` в запросе, `GITHUB_REPO` — только фоллбек
(раньше репо было жёстко одно на весь воркер и не масштабировалось на
несколько проектов). Токен — секрет `GITHUB_TOKEN`, без него сразу
`needs_input`.

Две вещи, на которые стоит смотреть при первом реальном запуске:
- Формы ответов GitHub API взяты **по знанию API, не проверены живыми
  запросами** — api.github.com отдал rate-limit на IP песочницы при попытке
  сверить. Эндпоинты давние и стабильные, но проверяется одним вызовом
  `list_commits`.
- `commit_file` кодирует содержимое через UTF-8 → base64 вручную, а не голым
  `btoa()`: последний падает на кириллице (`InvalidCharacterError`).

## Architect Agent

Планирует ДО написания кода: стек с обоснованием, разбивка на модули,
зависимости, риски и компромиссы. Плюс диаграмма компонентов в Mermaid
(блок `---DIAGRAM---`), которую дашборд рендерит в SVG.

Маршрутизация (Orchestrator):
- `analyze_spec` / `generate_code` → **Architect → Code Agent**. План уходит
  в Code Agent как `architecturePlan`, и тот следует ему вместо того, чтобы
  принимать архитектурные решения самостоятельно.
- `review_repo` → напрямую в Code Agent. В существующем репозитории
  архитектура уже есть — её надо ревьюить, а не проектировать заново.
- Если Architect вернул `needs_input`/`failed` — до Code Agent не доходит,
  результат отдаётся как есть (нет смысла кодить по несуществующему плану).

Mermaid тянется с CDN как ES-модуль. Если CDN недоступен — диаграмма
показывается исходным текстом, страница не ломается.

## Memory Agent

Не Durable Object, а модуль `src/lib/memory-agent.ts` поверх общей D1
(таблица `project_memory`) — сознательное решение: `subAgent()` даёт
изолированный инстанс НА РОДИТЕЛЯ, то есть у Orchestrator и Code Agent были
бы РАЗНЫЕ MemoryAgent даже для одного project_id. Памяти нужен один
согласованный источник правды — D1 и есть этот источник, модуль просто
даёт типизированный доступ.

Механика:
1. Перед анализом Code Agent вызывает `recallContext()` — компактный текстовый
   дайджест того, что уже известно про проект, уходит в system-промпт модели.
2. Модели явно объяснено в промпте: если по ходу анализа появилось что-то
   достойное запоминания (архитектурное решение, стиль кода, выбор технологии,
   повторяющаяся проблема, предпочтение) — добавить в конце ответа блок
   `---MEMORY--- ... ---END---` с category/key/value.
3. `extractMemoryFacts()` парсит блок, `rememberFact()` пишет в D1 через
   upsert (тот же key+category — обновляет значение, не плодит дубли).
   Блок вырезается из текста, который видит пользователь (`stripMemoryBlock`) —
   это служебная разметка, не часть ответа по задаче.

Смотреть: дашборд, секция "Case notes", или `GET /api/projects/:id/memory`.

## Пробелы

1. ~~D1-схема неполная~~ — **закрыто.** Коннектор переподключился, схема
   сверена с реальным содержимым `azrail-db` (не на глаз — прямым запросом
   к `sqlite_master`). При сверке обнаружилось: `users` и `projects` уже
   существовали ДО этой сессии (видимо, от того же захода 2026-08-06, что
   и старый плейсхолдер-воркер) — с более узкой схемой, чем в `schema.sql`
   этого проекта. `CREATE TABLE IF NOT EXISTS` в первом проходе поэтому
   молча ничего не добавил к `users` — предыдущее сообщение в чате про
   «таблица users применена» было неточным, на деле это был no-op на уже
   существующую таблицу. Исправлено через `ALTER TABLE ADD COLUMN`
   (`users.email`, `users.name`, `projects.description/stack/r2_prefix/
   updated_at`), затем досозданы `project_versions` и `task_history`.
   Также обнаружена лишняя таблица `sessions` (project_id/agent_type/
   context) — не используется этим кодом, похоже на набросок из той же
   ранней сессии под другую схему истории задач. Не трогал — не мой
   контекст, чтобы дропать. Если не нужна — скажи, удалю.

2. **Queue не создана.** В инструментах Cloudflare-коннектора нет операции
   создания Queue вообще (только D1/KV/R2). Для MVP не блокер —
   Orchestrator дожидается ответа sub-agent'а напрямую (`await`), без очереди.
   Когда понадобится async-диспетчеризация:
   `wrangler queues create azrail-tasks`, затем раскомментировать блок
   `[[queues.producers]]` в `wrangler.toml`.

3. **Vectorize не создан.** Code Agent пытается сделать retrieval
   (`retrieveKnowledge()`), но при отсутствии `env.AZRAIL_VECTORIZE`
   тихо продолжает без RAG-контекста — не роняет задачу, но и не
   выполняет то, что раздел 9 системного промпта требует как обязательное.
   Создать: `wrangler vectorize create azrail-knowledge --dimensions=1024
   --metric=cosine` (размерность под `@cf/baai/bge-m3` — проверено по докам:
   1024 dims, мультиязычная, 100+ языков, включая русский; исходно в коде
   стояла непроверенная `bge-base-en-v1.5`, англоязычная и 768 dims — заменил,
   не дошло бы до рассинхрона размерностей только по счастливой случайности), затем раскомментировать `[[vectorize]]` в
   `wrangler.toml`.

4. **AI Gateway / сторонние модели.** Сейчас используется только Workers AI
   (`@cf/...`) через `env.AI` — этого достаточно для MVP и не требует ключей.
   Если нужны OpenAI/Anthropic/Gemini — завести AI Gateway в дашборде и
   передавать модели в формате `{author}/{model}` в тот же `env.AI.run()`,
   плюс секреты из `.env.example`.

5. **Именование: Azrail vs Эпикс.** В памяти проекта отмечено, что агент
   переименовывался Azrail → Эпикс. Ресурсы в Cloudflare (`azrail-db`,
   `AZRAIL_KV`, `azrail-artifacts`, Worker `azrail-os`) уже созданы под
   именем Azrail отдельно от `dark-planet-*` — похоже на осознанно
   отдельный проект, а не переименование того же самого. Собрано как
   отдельная система; если это должно быть частью/преемником Эпикса —
   скажи, поменяю нейминг и, если нужно, свяжу с существующей D1
   `dark-planet-db`.
