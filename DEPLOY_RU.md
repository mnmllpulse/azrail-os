# Развёртывание на GitHub и Cloudflare

## 1. Что подготовить один раз

- Cloudflare-аккаунт с тремя зонами: `mnmllpulse.com`, `mnmllpulse.org`, `pulse-labs.org`.
- GitHub-репозиторий с распакованным содержимым ZIP **в корне**. Не загружайте ZIP вместо файлов.
- OIDC-приложение у выбранного провайдера входа. Поддержаны Authorization Code + PKCE, RS256/ES256, public client либо confidential client с `client_secret_post`.
- Разрешённые redirect URI: `https://mnmllpulse.com/auth/callback`, `https://mnmllpulse.org/auth/callback`, `https://pulse-labs.org/auth/callback`.

Пользовательские аккаунты создаёт OIDC-провайдер. Его настройки определяют, открыта ли регистрация. Сессии раздельные для каждого hostname; общий вход возможен через сессию провайдера, cookie не распространяется между несвязанными доменами.

## 2. GitHub Settings → Secrets and variables → Actions

Secrets:

| Имя | Значение |
|---|---|
| `CLOUDFLARE_ACCOUNT_ID` | Ваш account ID |
| `CLOUDFLARE_API_TOKEN` | Токен для Workers, D1, KV, R2 и custom domains; только нужный аккаунт/зоны |
| `OIDC_CLIENT_SECRET` | Если клиент confidential; не требуется для public PKCE client |
| `INTEGRATION_KEY` | Для MCP: постоянный ключ AES-GCM, 32 случайных байта в base64; сохраните резервную копию |
| `MCP_OAUTH_SECRETS` | Для MCP confidential clients: JSON-словарь policy ID → client secret |

Repository Variables:

| Имя | Значение |
|---|---|
| `ENABLE_DEPLOY` | `true` — включает workflow публикации |
| `DEPLOY_PROFILE` | `free` по умолчанию; `paid` включает Containers |
| `WORKER_NAME` | `azrail-pulse` по умолчанию |
| `OIDC_ISSUER` | Точный issuer из документации вашего IdP |
| `OIDC_CLIENT_ID` | ID OIDC-приложения |
| `OPERATOR_ACCOUNT_IDS` | После первого входа — ID вашего аккаунта из окна «Ваш аккаунт» |
| `MCP_SERVERS` | JSON allowlist; пустой массив оставляет подключения выключенными |
| `AI_GATEWAY_ID` | ID вашего Gateway, по умолчанию `default` |
| `DAILY_PROVIDER_CALLS` | Общий дневной лимит обращений провайдеров; по умолчанию 200 |

Никогда не кладите токены в HTML, `.env`, frontend или git. Не отправляйте их в чат. В production используется `AUTH_MODE=oidc`; `AZRAIL_TOKEN` не открывает доступ к новому приложению.

## 3. Первый запуск

Создайте GitHub Environment `production`, при необходимости ограничьте ветку main. После push в main workflow выполняет `npm ci`, сборку, тесты, provisioning, backup D1, миграции и deploy.

Provisioning повторно использует ресурсы с тем же именем. Он не переименовывает и не удаляет прежние базы. ID генерируются Cloudflare и записываются в `wrangler.generated.json`; нулевые ID в шаблоне не предназначены для реального deploy.

Если R2 ещё не включён, Cloudflare может потребовать активацию сервиса в кабинете. Профиль Free относится к Workers; отдельные сервисы имеют собственные лимиты и оплату.

После первого входа скопируйте свой ID, добавьте его в `OPERATOR_ACCOUNT_IDS` и повторно запустите workflow. Это даёт управление маршрутизацией, тарифами и разрешениями своих проектов, **не доступ к чужим проектам**.

## 4. Проверка на трёх доменах

1. Открыть каждый домен в браузере, проверить сертификат и вход.
2. Создать проект небольшим запросом; закрыть вкладку и найти его в «Проекты».
3. Проверить загрузку изображения, ALS, голосовой запрос и скачивание результата.
4. Войти вторым аккаунтом: проекты и файлы первого не должны быть доступны.
5. Повторить POST с тем же Idempotency-Key: тот же результат, без нового вызова провайдера.
6. Включать сторонние модели только после заполнения бюджета, проверки Gateway и актуальных тарифов.

Это обязательная живая приёмка: локальные тесты используют SQLite и имитации ответов внешних провайдеров.

## 5. Paid Sandbox

Поставьте `DEPLOY_PROFILE=paid`. Это изменение может создавать платные контейнеры; оно не является частью бесплатного режима. Образ закреплён на `cloudflare/sandbox:0.12.9-python`. После изменения профиля не откатывайте Worker на Free-конфиг поверх уже применённых миграций Sandbox.

Оператор разрешает Sandbox выбранному проекту кнопкой в карточке миссии. Сеть контейнера закрыта по умолчанию. Проекты, которым нужны внешние зависимости, требуют заранее подготовленного образа либо отдельного контролируемого этапа установки зависимостей. Произвольный `npm install` при закрытой сети не будет работать. Незавершённая проверка останавливает отметку готовности; эта поставка не маскирует её успешным статусом.

## 6. Оплата и каталог

OFF блокирует сторонние и требующие оплаты маршруты текстового роутера. На Workers Paid даже Cloudflare-hosted модели могут превысить бесплатную квоту. Студии Flux/Whisper используют Workers AI напрямую; их Neurons входят в общий расход аккаунта.

Unified Billing Cloudflare использует prepaid credits. Внешние вызовы допускаются при разрешённом Hybrid-режиме, Gateway, свежем проверенном тарифе и достаточном резерве. Нужен реальный Gateway с ID `default` или другое значение `AI_GATEWAY_ID` при локальном provisioning.

`/api/model-catalog` читает актуальный каталог binding. Его размер может отличаться от объединённого каталога dashboard. Число 229 не зашито как гарантия совместимости. Новая модель требует проверки схемы входа/выхода и тарифа, а не только добавления названия.

## 7. Перенос старых данных

Миграции 008 и 009 добавляют таблицы без удаления старых записей. Данные прежнего AZRAIL можно переносить в существующие совместимые D1/R2 после backup и назначения владельцев `resource_owners`. Пользовательские PULSE/Firebase данные автоматически не импортируются: их live-export отсутствует в ZIP, а схема и принадлежность записей должны быть проверены отдельно.

Backup кода в R2 и backup D1 независимы. Перед миграцией скрипт делает SQL-export. Для JSON-конфига remote-export автоматически копируется в приватный R2-префикс `ops/backups/` до применения SQL; при ошибке копирования миграция останавливается. Сохраните также независимую копию. Ephemeral GitHub runner не является долговременным хранилищем backup. Для production дополнительно настройте D1 recovery/retention и независимые R2 backups.

## 8. Локальный план без публикации

```sh
npm ci
npm run check
npm run provision
npm run build:check
```

Локальный реальный запуск, когда переменные окружения уже настроены:

```sh
npm run deploy:ci
```

Если вместо GitHub Actions используете Cloudflare Workers Builds, задайте build command `npm run check`, deploy command `npm run deploy:ci` и те же environment variables. Используйте один механизм публикации, чтобы два pipeline не меняли Worker одновременно.

## 9. Приёмка подключений и новых функций 1.3

Настройка OAuth callback, scopes и vault: [docs/CONNECTORS_RU.md](docs/CONNECTORS_RU.md). При каждом deploy сохраняйте тот же INTEGRATION_KEY, иначе старые подключения/результаты не расшифруются. Отсутствующий секрет pipeline не удаляет автоматически; отзыв должен быть отдельным намеренным действием.

После deploy проверьте: сохранение черновика в двух вкладках с конфликтом revision; стиль только собственного проекта; OAuth и повтор callback; discovery; сначала безвредное чтение, затем явно подтверждённое обратимое изменение; повтор его ID без второго эффекта; отключение доступа. Используйте тестовый аккаунт сервиса и минимальные scopes.

Рабочий catalog MCP появляется только после реальной настройки. Не вставляйте случайные community endpoints и не помечайте платные инструменты как бесплатное чтение. Новый gateway имеет request quota, а не защиту от любого счёта внешнего сервиса.

Оставшиеся задачи до публичного запуска: [docs/TASK_1.3_RU.md](docs/TASK_1.3_RU.md). Сборка 1.3 не является подтверждением live production deploy.


## Обновление 1.3.1 после аудита

В этой версии нет новой SQL-миграции: используются прежняя схема и миграции до 009 включительно. Для установленной 1.3 сохраните D1, R2, OIDC и ключ шифрования интеграций; применяйте код после сопоставления с вашей веткой. В workflow перед первой записью в Cloudflare проверяются параметры OIDC, профиль, формат JSON-конфигурации и дневной лимит; frontend пересобирается до provisioning.

`deploy/free.json` и `deploy/paid.json` — шаблоны для генерации корневого `wrangler.generated.json`. Их пути (`src/`, `site/`, `Dockerfile`) рассчитаны на итоговый файл в корне. Для проверки Paid без публикации скопируйте шаблон в корень под временным именем и запускайте Wrangler с ним; не запускайте шаблон напрямую из `deploy/`. Удалите временный файл после проверки. Production workflow делает это через `scripts/provision.mjs`.

`DAILY_PROVIDER_CALLS=0` останавливает новые учитываемые вызовы уже в текущие сутки. Это лимит количества запросов, а не гарантия нулевого счёта Cloudflare. Записи успешных и неопределённых операций больше не удаляются автоматически через сутки. Увеличение D1-хранилища нужно учитывать; очистка таких записей допустима только после сверки результата и разработки отдельной retention-политики. Уже удалённые прежней версией записи восстановить этим обновлением нельзя.

После публикации проверьте вход, понижение роли до viewer, одну разрешённую миссию, её восстановление после перезагрузки и скачивание ZIP с изображением. Сверьте фактические расходы в аккаунте. Не считайте локальный dry-run проверкой DNS, OIDC-провайдера или контейнера.
