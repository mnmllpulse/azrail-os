# AZRAIL × MNMLL PULSE OS — аудит и доработки 1.4.0

Дата: 3 октября 2026 года. Вход: AZRAIL_PULSE_Unified_1.3.1.zip. Результат: исправленная сборка 1.4.0.

Глобус убран из рабочего интерфейса. Все девять действующих модулей студий получили отдельные страницы. Исправлены потеря черновиков, гонки при переходах, освобождение медиа, обработка ошибочных ответов, несколько серверных проверок и дублирование CI. Есть отчёты CSV/ALS/расходов и полезная диагностика Pulse Lab.

**Статус приёмки:** 1181 тест в 57 наборах, TypeScript, сборка интерфейса и Free/Paid Worker dry-run прошли. В настоящем Chromium проверены все девять студий, Back/Forward, reload, WAV/MIDI, WebM, CSV и компоновка на 320/390/768/1440 px. Боевой OIDC, фактические ответы Workers AI, OAuth сервисов, Docker и реальный счёт Cloudflare требуют проверки в установленном приложении. Локальные проверки не дают основания заявлять коммерческую готовность всех задуманных студий.

## 1. Что находится в архиве

В исходном ZIP — 656 записей, около 11,7 МБ распакованных данных. Архив распакован с проверкой путей и символических ссылок. Инвентаризация отделяет работающую сборку от архивных материалов:

| Область | Реальный статус |
|---|---|
| `ui/` | Основной интерфейс Unified, который собирается в `site/` и корневой `index.html` |
| `src/unified/` | HTTP-граница: OIDC, студии, черновики, MCP/OAuth, контракты дизайна, ресурсный журнал |
| `src/core`, `src/agents`, `src/lib` | Движок миссий, файлы, агенты, проверки, владение, бюджеты, версии, восстановление |
| `site/` | Собранные файлы для Worker Static Assets; здесь нет архивных консолей |
| Корневой `index.html` | Автономный просмотр и локальные инструменты; не требует загрузки CSS/JS из сети |
| `public/` | Исторические интерфейсы и старые тестовые контракты; основной deploy обслуживает `site/` |
| `references/pulse-source/` | React-исходники другого приложения, не подключённые автоматически к текущему production |
| `references/globe.html` | Исторический исходник прежнего эффекта; в рабочую сборку 1.4 не входит |
| `docs/` | Предыдущие аудиты и сценарии. Актуальная инструкция — README и этот отчёт |

Проверены действующие точки входа, UI-модули, маршруты студий, доступы, черновики, CSV/ALS, контракты внешних действий, сборка, CI и существующие тесты. Старые документы и архивные панели использованы для поиска расхождений и незавершённых функций. Полнота production-поведения оценивается по коду и проверкам, а не по количеству названий в меню.

| 15 | P2 | Некорректная `%`-кодировка имени загружаемого файла давала 503 | Получается 400 до записи в R2. Пустое имя получает корректный fallback |
| 16 | P2 | CSV с BOM/`;`/табуляцией мог давать неверную структуру | Определение распространённых разделителей, BOM, CR/CRLF; проверка кавычек и ограничение числа ячеек/столбцов/строк |
| 17 | P2 | Среднее больших конечных чисел могло превращаться в Infinity | Среднее вычисляется с предварительным делением слагаемых |
| 18 | P2 | CSV, ALS и расходы показывали преимущественно сырой JSON | Основные показатели представлены таблицами. JSON доступен в свёрнутом отчёте и для скачивания |
| 19 | P2 | Два одинаковых workflow Verify запускали одни и те же проверки | Удалён дубль `verify.yml`; сохранён `check.yml` и отдельный deployment workflow |
| 20 | P1 | Smoke-скрипт принимал только Bearer, который отключён в основном OIDC-режиме | Добавлен `AZRAIL_SESSION_COOKIE`. Старый token mode поддерживается; секреты не выводятся |
| 21 | P2 | Отдельные символы и автоматический focus заголовка ухудшали вид мобильной страницы | Кнопка вложения использует совместимый знак +; программный focus заголовка не превращает его в подобие поля ввода |

Автономный HTML: **1 025 455 → около 115 100 байт**, уменьшение примерно **88,8%**. Это размер несжатого preview. Основной hosted JS вырос из-за навигации и восстановления состояния; тяжёлый 3D-код полностью вышел из рабочего графа импортов. Не заявляется ускорение сервера или уменьшение общей цены Cloudflare из одного этого измерения.

## 3. Все действующие страницы студий

| Модуль | Адрес в развёрнутом приложении | Основное действие | Результат |
|---|---|---|---|
| Сайты и приложения | `/studios/web` | Создать | Миссия, ход работы, проверка, ZIP проекта |
| Изображения | `/studios/image` | Создать изображение | Workers AI; изображение и файл в аккаунте |
| Музыка | `/studios/music` | Создать эскиз | Алгоритмический синтез F minor; прослушивание, WAV, MIDI |
| Видео | `/studios/video` | Записать видео | 8 секунд типографической анимации; WebM |
| Аудиоанализ | `/studios/audio` | Проанализировать аудио | PCM-уровни, спектр, сравнение с референсом, JSON |
| Ableton | `/studios/als` | Проанализировать ALS | Таблица треков, темп, роли, JSON |
| Данные | `/studios/data` | Проанализировать CSV | Таблица заполненности и статистики, JSON |
| Расходы | `/studios/ledger` | Обновить журнал | Лимит запросов платформы и вызовы моделей своих проектов |
| Pulse Lab | `/studios/lab` | Проверить доступность | Совместимость браузера и наличие серверных bindings; JSON |

При открытии корневого HTML те же экраны имеют переносимые адреса `#/studios/music` и т. п. Обычные ссылки поддерживают новую вкладку; история браузера и прямой переход сохраняют выбранный модуль. Неизвестный модуль показывает страницу «Не найдено». Старые адреса `/studio/music` распознаются интерфейсом для совместимости.

Страницы используют общий shell и одну точку сборки. Это отдельные пользовательские экраны с URL, а не девять несогласованных HTML-копий. Новая схема не требует SQL-миграции.

Черновики музыки/изображений/видео сохраняются локально в сессии и, после входа, могут записываться на сервер с revision. Web Studio использует локальный черновик запроса; исполнение миссии хранится сервером. Файловые input не восстанавливаются после reload автоматически. Закрытие вкладки может завершить sessionStorage; для долговременной работы нужен серверный черновик или скачанный файл.

## 6. Как усилить архитектуру и логику дальше

1. **Свести задания в исполняемый контракт.** Сейчас есть MissionSpec/ToolCall/ResourceReservation, а ядро сохраняет совместимые старые DTO. Нужна runtime-валидация всего payload, единая версия контракта и переходы состояний, проверяемые сервером. TypeScript-интерфейс сам по себе не валидирует внешний JSON.
2. **Сделать сервер владельцем состояния задания.** UI хранит адрес страницы и редактируемые поля; сервер хранит job ID, progress, revision, artifact ID и доказательство проверки. Перезагрузка должна восстанавливать эти значения без повторного provider dispatch.
3. **Разделить жизненные циклы.** Переключение страницы прекращает отображение локального запуска; отмена серверной миссии — отдельное действие. Отмена transport не означает, что платный внешний эффект не произошёл.
4. **Привязать артефакт к происхождению.** Нужны account/project/job/module, source/input digest, MIME, размер, версия, checks, время и ссылка на ресурсную операцию. Это позволит доверять истории и отличать пересоздание от восстановления результата.
5. **Добавить квоты на аккаунт и хранилище.** Есть общий дневной request-budget и денежные резервы моделей. Для studio uploads не реализована полноценная квота объёма/retention по аккаунту. Нужны byte accounting, лимит количества артефактов, удаление и освобождение резерва.
6. **Сверять реальные единицы расхода.** Request limit не является Neuron meter или общим счётом Cloudflare. Нужны фактические AI units, R2/storage, Sandbox seconds и сверка с провайдером. Не заполнять неизвестную стоимость нулём.
7. **Ограничить CPU/память каждого анализатора.** CSV теперь ограничен. Для ALS нужен дополнительный бюджет глубины/числа XML-узлов/треков. Для аудио нужна проверка доступной памяти и worker-поток обработки; декодирование сжатого файла может быть тяжёлым до определения его длительности.
8. **Убрать зависимость долгой работы от открытой страницы.** WebM сейчас записывается в браузере, а throttling скрытой вкладки меняет практическое время работы. Для длинных задач нужен job runner, очередь, heartbeat и восстановление после остановки runtime.
9. **Использовать общий capability registry.** Новый `ui/studios.ts` уже объединяет название, URL, описание и действие действующих студий. Следующий шаг — общий типизированный контракт с сервером: input/output schema, permission, execution mode, availability и version.
10. **Переносить старое приложение через адаптеры.** PULSE/Firebase/React-панели требуют сопоставления данных и API. Не подмешивать второй несогласованный store в текущую страницу и не копировать старые состояния «успех».

## 7. Порядок завершения продукта

| Этап | Состав | Критерий приёмки |
|---|---|---|
| A — проверить установку | OIDC, основной домен, реальные D1/KV/R2, AI, OAuth, Free/Paid профиль | Два реальных аккаунта изолированы; вход/выход работают; каждый разрешённый provider возвращает реальный результат |
| B — завершить проектный цикл | Файлы, preview, редактор, проверки, версии, backup | Один проект создан, изменён, проверен, экспортирован и восстановлен без потери файлов |
| C — завершить работу студий | Project artifacts, history, server drafts, quotas | Повтор, timeout, reload и конфликт не создают лишний платный эффект и не теряют введённые параметры |
| D — перенести необходимые студии | Code → Sandbox → Deploy → Knowledge → Agent Forge; остальные после подтверждения потребности | У каждого переносимого модуля реальное исполнение, файл результата, права и проверяемые статусы |
| E — эксплуатация | Мониторинг, нагрузка, reconciliation, backup drill, мобильные реальные устройства | Проверены отказ БД/провайдера, переполнение бюджета, восстановление и задержки на слабой сети |

Для главной достаточно трёх разделов: Создать, Проекты, Студии. На странице модуля — задача, необходимые поля, одно основное действие и результат. Технические параметры и подробный JSON раскрываются по необходимости. Агенты могут выбирать техническую конфигурацию в границах разрешений и бюджета; сервер остаётся источником этих ограничений.

Шестисекундная понятность не доказана автоматическим тестом. После технической приёмки провести короткий пользовательский тест: человек без подсказки должен за шесть секунд назвать следующее действие, ожидаемый результат и доступный инструмент. Фиксировать время и ошибки выбора.

## 8. Интеграции и источники проверки

- **GitHub:** прочитаны metadata репозитория `mnmllpulse/azrail-os` и текущий `package.json` в `main`. В нём другая структура скриптов, в том числе `build:pulse` и staging-проверки. ZIP и main являются разными поставками; перенос требует сопоставления в отдельной ветке. Изменения этого аудита выполнены в архиве. Ссылки: [репозиторий](https://github.com/mnmllpulse/azrail-os), [package.json](https://github.com/mnmllpulse/azrail-os/blob/main/package.json).
- **Canva:** прочитаны тексты двух страниц концепта AZRAIL OS, найденного в аккаунте. Использованы как ориентир простой структуры «Создать / Проекты / Студии» и одной формы запроса. Макет Canva не заменяет работающее поведение приложения. [Концепт](https://www.canva.com/d/Tra-t0jVBC-l9vO).
- **Cloudflare:** проверена официальная документация Worker Static Assets и Worker-first routing. В обоих профилях `run_worker_first: true`; страницы проходит защищённый обработчик, отдающий `app.html`. [Worker Script](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/), [SPA routing](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/).
- **Base44:** поиск приложений аккаунта по AZRAIL не вернул связанного приложения. В архиве отсутствует `base44/config.jsonc`. Перенос в Base44 — отдельная интеграция, а не действие, выполненное в этой сборке. Если он нужен, сначала определить canonical backend и адаптеры авторизации, хранения и заданий.
