# Следующие этапы AZRAIL

Цель — надёжный продукт с понятным первым действием. Количество агентов и моделей само по себе не доказывает качество.

## 1. До публичного многопользовательского запуска

| Задача | Что добавить | Критерий приёмки |
|---|---|---|
| Аккаунты | OIDC/Cloudflare Access либо выбранный провайдер идентификации; серверная сессия; выход и отзыв | Чужая сессия не читает и не изменяет ни один ресурс другого пользователя |
| Изоляция | tenant_id во всех таблицах и R2-префиксах; ownership-проверки на HTTP, WS и инструментах | Набор отрицательных тестов на перебор projectId/conversationId/r2Key |
| Полномочия агентов | Разделить чтение, изменение, Git и deploy; проверять разрешение при исполнении, не только в промпте | Агент не может получить полномочия из текста документа или ответа модели |
| Секреты | Пользовательские интеграции и scoped credentials, ротация, редактирование логов | Токен не появляется в артефакте, журнале или sandbox environment без необходимости |
| Администрирование | Настройки в закрытой панели, обычному пользователю — только нужные действия | Пользователь создаёт задачу, не выбирая инфраструктурные параметры |

## 2. Надёжность выполнения

| Задача | Реализация | Критерий приёмки |
|---|---|---|
| Outbox | Миссия и запись задания в одной транзакции; отдельный доставщик | Сбой между записью и запуском не теряет задание и не создаёт дубль |
| Checkpoints | Сохранять шаг, вход, выход, версию workspace и статус инструмента | Перезапуск после каждого шага продолжает работу предсказуемо |
| Fencing | Номер владения проектом у каждой записи; reject устаревшего исполнителя | Проснувшийся старый процесс не перезаписывает новый результат |
| Общий write lock | Охватить миссии, task, Git и restore | Нет одновременных конфликтующих изменений одного проекта |
| Отмена | AbortSignal там, где поддерживается; контроль остановки инструментов | После отмены не начинается новый платный или изменяющий шаг |
| Версии | Immutable manifest и атомарная смена ссылки на активную версию | Восстановление большого проекта не оставляет смесь двух версий |
| Восстановление | Backup D1/R2 и учебный restore в отдельную среду | Проверяемые RPO/RTO, успешное восстановление тестового проекта |

## 3. Стоимость и качество

- Записывать каждый вызов модели: модель, provider request ID, входные/выходные токены, цену, retry и длительность.
- Резервировать бюджет до запуска; сверять по факту; ограничивать стоимость на миссию, пользователя и сутки.
- Не запускать автоматические ретраи необратимых инструментов без idempotency key.
- Проверять доступность моделей реальным коротким вызовом по запросу администратора; хранить результат и дату.
- Создать независимый benchmark из реальных задач: сборка, исправление бага, регрессия, работа с ZIP, откат, отказ сети, prompt injection.
- Сравнивать версии по доле решённых задач, регрессиям, цене успешной задачи и p95 времени. Название «топ-1» допустимо только при прозрачной методике и измеренном результате.

## 4. Интерфейс по правилу шести секунд

Основной экран: поле «Что нужно сделать?», вложение, одна кнопка запуска. После запуска: текущий этап, результат, отмена. Выбор модели — «Авто» по умолчанию, ручной выбор в дополнительном разделе. Технические настройки — в администрировании.

Студии и лаборатории показывать в общем каталоге с короткой задачей каждой. Не выдавать их за независимые работающие модули, пока не подтверждены backend-возможности. Для каждой карточки явно различать «доступно», «нужно подключение», «запланировано».

Проверка: дать новому человеку реальную задачу без объяснения интерфейса; измерить время до первого верного действия и частоту ошибок. Проверить мобильный экран, клавиатуру, контраст, возврат после перезагрузки и понятные ошибки квоты/сети.

Canva имеет смысл использовать для визуальной системы и прототипа после фиксации сценариев. Для проверки backend и ZIP редактирование дизайна не требуется. Отдельного подключённого OpenAI Developers-инструмента в этой сессии не было; внешние модели используются через существующий Cloudflare AI Gateway, их работоспособность в аккаунте не проверена.

## 5. Релизный шлюз

1. Локальный `npm ci`, `npm run check`, `npm run build:check`.
2. Docker-сборка Sandbox, совпадение версии SDK/образа.
3. Staging Cloudflare: миграции, DO lifecycle, WebSocket, R2, Gateway.
4. Нагрузочные проверки: конкурентные повторы, лимиты, зависания и отмена.
5. Проверка восстановления из резервной копии и отката релиза.
6. Ограниченный запуск на реальных задачах с метриками; только затем расширение аудитории.

Архитектурно сначала закрываются пункты 1–2. Массовое добавление новых агентов, лабораторий и моделей до этого увеличивает поверхность ошибок.
