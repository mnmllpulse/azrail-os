# Инженерный аудит AZRAIL OS

## Вывод

Проект содержит работающую основу: Worker, оркестратор, специализированные агенты, хранилище проектов, фоновые миссии, инструментальные действия, проверки результата и браузерный интерфейс. Исходные 913 тестов и TypeScript проходили. Это не означало отсутствие ошибок: значительная часть тестов проверяла текст исходников и не обнаруживала обходы защиты или ошибки порядка выборки SQL.

Версия 0.6.3 исправляет подтверждённые проблемы в доступе, расходах, повторах, ZIP, откатах и контексте чата. Называть её полностью проверенной многопользовательской платформой мирового уровня пока нельзя: реальные интеграционные, нагрузочные и аварийные проверки ещё нужны.

## Что осталось слабым

1. **Один общий секрет.** Нет пользовательской аутентификации, RBAC и tenant-bound запросов. projectId и conversationId не являются правом доступа. Публичный многопользовательский запуск пока не готов.
2. **Блокировка охватывает только вход миссий.** `/api/task`, Git, восстановление версий и другие записи требуют общей координации. Cron может признать длительную миссию зависшей, пока процесс ещё жив: нужен fencing token, а не один статус.
3. **Нет сквозного exactly-once.** Захват запроса атомарен, но запись миссии, scheduling и сохранение ответа — отдельные операции. После неоднозначного сбоя резерв остаётся, чтобы не создавать дубль. Нужны transactional outbox и reconciliation.
4. **Квоты не являются биллингом.** Планирование, рефлексия, fallback, retry и токены увеличивают расход относительно числа итераций. Требуется ledger каждого вызова провайдера, резерв денег и сверка факта.
5. **R2-откат не транзакционен.** Защита от неполного списка добавлена, но несколько put/delete нельзя атомарно переключить. Нужны неизменяемые версии и указатель активного manifest. Предел снимка сейчас 1000 файлов / 16 МиБ. Неудачный снимок возвращает null, миссия по прежней логике может продолжаться без страховки.
6. **Долгие операции и отмена.** withTimeout перестаёт ждать Promise, но не обязательно отменяет внешний вызов. Отмена миссии проверяется на границах шагов. Нужны abort propagation, lease/heartbeat и durable checkpoints.
7. **Сеть песочницы.** Фильтрация строк shell-команд не заменяет изоляцию сети, секретов и полномочий. Нужны allowlist egress, capability-bound tools и отдельные sandbox на tenant/mission.
8. **Чтение крупных файлов.** ZIP ограничен, но часть остальных путей чтения R2/GitHub по-прежнему буферизует ответ до усечения текста. Нужен общий потоковый ридер и пагинация.
9. **GitHub private sources.** При чтении raw.githubusercontent.com source-reader не передаёт GitHub-токен; приватный репозиторий может дать пустой контекст. Нужен authenticated Contents API с таймаутом и лимитом.
10. **Реестр моделей.** Наличие AI Gateway не доказывает доступность всех его моделей. Нужны реальные smoke-тесты разрешённых моделей, проверка capabilities и тарифов в аккаунте.
11. **Проверка CVE самим Azrail.** parseDependencies убирает префикс диапазона из package.json; это не гарантирует установленную версию. Следует анализировать lockfile/SBOM.
12. **Наблюдаемость.** Нужны единый request/mission trace, метрики стоимости/ошибок/очереди и сигналы об авариях. Сейчас есть структурные логи, но операционный контур неполон.
13. **Данные.** Требуются политика retention, удаление пользовательских данных, backup/restore drill и ограничения объёма загрузок на аккаунт. Multipart остаётся буферизованным в заданном пределе.
14. **Тесты.** Новые SQL/HTTP проверки исполняют логику, но используют локальную SQLite и заглушки Cloudflare. Они не заменяют workerd/Miniflare и проверку живых DO, R2, AI и контейнеров.
15. **Документация.** В старом README и комментариях накопились исторические утверждения. Для изменений 0.6.3 первичны START_HERE_RU.md и этот отчёт; полная редактура старой документации не выполнена.

## Важные ограничения результата

Проверка была ориентирована на реальные найденные риски и пути обработки, а не на формальную верификацию каждой строки. Полного пентеста, проверки каждого model slug, UI-теста браузером, аудита доступов облачного аккаунта и измерения качества против конкурентов не было. 0 уязвимостей npm означает отсутствие известных совпадений в полученном отчёте на момент проверки, а не доказательство полной безопасности.

Официальный ориентир по Worker: https://developers.cloudflare.com/workers/best-practices/workers-best-practices/ . Конкретные ошибки выше установлены по исходникам и воспроизводимым проверкам проекта; источником истины для использованных SQL стали исполняемые тесты SQLite.
